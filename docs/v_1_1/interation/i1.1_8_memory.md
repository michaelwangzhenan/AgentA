# 内存审查

## 1. 背景

进入知识库二级文档列表时，VPS 内存曾快速升高并死机。原实现为了统计文档字符数，通过 collection.get(include=["metadatas", "documents"]) 一次读取知识库全部 chunk 正文。知识库规模增大后，这个列表请求会产生远超页面展示需要的内存峰值。

该问题已在 i1.1_7_real_site.md 第 3.2.8 节记录并修复。为了避免其他入口重复出现“只需少量摘要，却把全量正文读入内存”的问题，本次继续审查 AgentA 全部生产代码，重点检查：

- 随数据量增长的常驻内存；
- 单次请求或任务产生的峰值内存；
- 并发请求造成的倍增；
- 无容量上限的队列、缓存和集合；
- 全量读取、重复复制及未释放资源。

## 2. 审查范围

本次覆盖以下生产代码：

- src/rag：文档解析、分块、Embedding、Chroma、BM25、检索和精排；
- src/agent、src/llm：Agent 循环、工具调用、深度研究、模型调用和流式输出；
- src/api、src/services、src/stores：API、会话、缓存、备份、巡检、统计和数据库访问；
- frontend/src：聊天、知识库、附件、管理页和流式渲染。

测试与评估脚本只检查是否会被线上入口调用。本次是静态代码审查，没有连接 VPS 采集 RSS（Resident Set Size，常驻内存集）、堆快照或压力测试。因此，文中数量级是根据数据结构和调用链估算的，实施前仍需用实际数据验证。

优先级含义：

- P0：低内存 VPS 的常规路径可能直接触发 OOM（Out of Memory，内存不足），需要先处理；
- P1：现实负载下会产生明显峰值或长期增长，应在近期处理；
- P2：需要特定操作、较大数据量或较长运行时间才明显，可分批治理；
- P3：影响很小、已有明确上限，或属于可接受的短期管理开销，本期不安排。

## 3. 已修问题

### 3.1. L2列表

src/rag/ingest.py 第 424-495 行已经把知识库二级列表改为：

- 只读取 metadata，不读取 chunk 正文和向量；
- 每批读取 256 条 metadata；
- 新入库的 chunk 写入 char_count，列表直接聚合字符数；
- 老数据没有 char_count 时按 0 计算，不再为了补字符数读取正文。

该修改解决了原问题中最直接的全库正文读取。tests/rag/test_kb_list_documents.py 已覆盖分批读取行为。

不过，列表仍会扫描全部 chunk，并在内存中保存全部文档级聚合结果。因此它从“正文规模风险”降为“文档数量风险”，还没有实现真正的服务端分页，详见第 6.1 节。

## 4. 核心结论

审查共列出 17 项需要处理的问题：P0 1 项、P1 8 项、P2 8 项。

当前最大的风险不是已修复的 L2 列表，而是 BM25（Best Matching 25，概率相关性检索算法）索引。BM25Index 会同时保存每个 chunk 的完整正文、分词结果和词频表，并把访问过的 collection 缓存在进程中。大知识库首次检索或入库时，索引整体载入后会持续占用内存，直到清空知识库或重启进程。

第二类风险来自全量读取和重复复制，包括大文件入库、网页抓取、会话历史、备份还原及数据库巡检。第三类风险来自并发和流式处理：一个 Agent run 本身有边界，但默认最多四路并发，深度研究还会在每路内部并行子代理；慢客户端又可能让无上限的流式事件队列继续增长。

建议先处理 BM25、输入字节上限、会话分页和流式队列，再优化管理页和前端分配压力。

## 5. P0问题

### 5.1. BM25常驻

位置：src/rag/bm25_index.py 第 135-140、182-207、252-315 行；src/rag/ingest.py 第 251-261 行；src/rag/retriever.py 第 271-309 行。

首次 BM25 检索、文档入库或删除都会调用 get_index。load_or_new 使用 pickle.load 一次反序列化整个索引，随后 _index_cache 按 collection 长期持有 BM25Index。

一个 chunk 在索引中至少以三种形式存在：

- BM25Doc.document 保存完整正文；
- BM25Doc.tokens 保存分词后的字符串列表；
- _tf 保存每个 chunk 的词频 Counter。

此外还有 metadata、文档长度、词频逆文档频率和 Python 对象本身的开销。中文 bigram 分词会产生大量短字符串，实际内存通常明显大于 pickle 文件大小。索引规模为 O(全库 chunk 数)，没有条目上限，也没有冷索引淘汰。drop_index 只在清空整个 collection 时调用。

粗略估算，1 万个约 600 字符的 chunk 可能占 30-80 MB；10 万个 chunk 可能占 300-800 MB。实际值受中英文比例、重复字符串和 Python 版本影响，需要以 VPS 测量为准。

处理建议：

1. 先统计每个 bm25_*.pkl 文件大小，并记录首次检索前后的进程 RSS；
2. 在低内存 VPS 暂时关闭 BM25，与只用 Dense 检索的基线对比；
3. 中期把 BM25 改为磁盘倒排索引或按需加载，不再以 Python 对象保存全库；
4. 若暂时保留当前实现，保存索引后淘汰冷 collection，并限制同一进程常驻索引数量。

## 6. P1问题

### 6.1. 入库峰值

位置：src/rag/ingest.py 第 170-261 行；src/rag/parser.py 第 105-150 行；src/rag/splitter.py 第 167-244 行。

POST /api/kb/upload 入库大文件时，代码先把解析后的全文保存为一个字符串，再一次生成全部 Chunk。随后又构造 ids、documents 和 metadatas 三个完整列表。Chroma 虽然每批只写入 16 个 chunk，但这些全量列表已经在分批循环之前创建。

启用 BM25 后，upsert 还会复制正文并生成全部 tokens；save_index 会遍历并序列化整个 collection 的索引。单文件 10 MB 上限并不等于 10 MB 内存峰值，因为字符串、列表、字典和分词对象会把占用放大到数十 MB甚至更高。

处理建议：

- 把解析、分块、Embedding 和写入改为流水处理，不同时保存全量 documents；
- 为单文档 chunk 数设置硬上限；
- BM25 改为增量写入持久化索引，避免每次入库重写整个 collection；
- 为入库任务设置独立并发上限，避免多个上传同时放大峰值。

### 6.2. 网页抓取

位置：src/agent/tools.py 第 675-781 行。

fetch_url 使用 requests.get 获取网页。requests 默认先把完整响应体读入内存，随后 response.content、response.text 和 BeautifulSoup 解析树还会产生额外副本。max_chars 只限制最终返回给大语言模型的正文，不限制下载和解析阶段。

Jina Reader 回退路径也会先读取完整 resp.text。超大 HTML、异常服务器或恶意响应可以让单次工具调用占用大量内存。深度研究允许多个子代理并行抓取，风险还会按并行数放大。

处理建议：

- 增加 MAX_FETCH_BYTES，建议先设 2-5 MB；
- 使用 stream=True 分块读取，累计超过上限立即中止；
- 同时检查 Content-Length，但不能只依赖该响应头；
- Jina Reader 路径使用同一字节上限。

### 6.3. 会话全读

位置：src/stores/session_store.py 第 162-189 行；src/api/routes/sessions.py 第 130-149 行；frontend/src/hooks/useChat.ts 第 107-130 行；frontend/src/components/chat/MessageList.tsx 第 64-81 行。

Agent 自己加载历史时会先取最近 160 条消息，再按最近 20 轮精确截断。但前端打开历史会话时，GET /api/sessions/{session_id}/messages 调用 SessionStore.load，通过 fetchall 读取该会话全部消息。

后端会反序列化全部 tool_calls 并一次构造响应。前端再把完整 Message 数组写入 React 状态，并通过 messages.map 全量挂载。每条助手消息还可能包含 Markdown、thinking、工具时间线、计划和深度研究状态。长会话会同时放大后端响应、浏览器堆和文档对象模型节点数量。

处理建议：

- 消息 API 增加 limit 和 before_id 游标；
- 首次只返回最近若干轮，用户向上滚动时再加载更早消息；
- 前端对消息列表使用窗口化渲染，只挂载可见区域附近的消息；
- 历史中的工具正文只保留摘要，完整结果按需读取。

### 6.4. SSE队列

位置：src/api/routes/chat.py 第 368-407、466-482 行。

流式聊天使用 SSE（Server-Sent Events，服务器推送事件）把 Agent 线程产生的事件送到浏览器。当前 asyncio.Queue 没有 maxsize，生产者通过 put_nowait 持续入队。

客户端很慢、反向代理发送不及时或浏览器断开时，Agent 仍会继续执行。代码只取消 asyncio 包装任务，线程池中的同步 agent.run 不会真正停止。尚未消费的 token、thinking 和工具事件会留在队列中，直到本轮自然结束。默认最多四路 Agent 同时运行，队列峰值可能叠加。

处理建议：

- 为队列设置 maxsize；
- token_chunk 按时间或字符数合并后再入队；
- 队列满时丢弃可合并的进度事件，final_answer 和 error 等终态事件必须保留；
- 增加协作式取消标志，让 Agent 和深度研究在客户端断开后尽快停止。

### 6.5. 备份还原

位置：src/api/routes/backup.py 第 102-126 行；src/services/runtime_backup.py 第 215-231 行。

管理员上传备份时，await file.read 会先把整个 zip 文件读入内存，而且没有大小上限。还原时，zf.read(e["arc"]) 会把每个归档成员完整解压到 bytes，再调用 write_bytes 写入磁盘。

包含 Chroma 和 BM25 的备份可能达到数百 MB甚至 GB。即使 zip 本身压缩后不大，单个成员解压后的大小也可能远大于上传文件，造成明显内存峰值。

处理建议：

- 为备份上传设置压缩包大小和解压后总大小上限；
- 检查每个 ZipInfo.file_size，拒绝异常压缩比；
- 使用 zf.open 配合 shutil.copyfileobj 流式解压；
- 还原大向量库时进入维护状态，避免与聊天和入库并发。

### 6.6. 本地模型

位置：src/rag/retriever.py 第 65-100 行；src/rag/reranker.py 第 30-50 行。

本地 SentenceTransformer Embedding 模型按模型名写入 _embedding_fn_cache，CrossEncoder 精排模型写入 _cross_encoder_cache。两个缓存都没有淘汰。运行时切换模型后，旧模型仍可能留在进程中。

单个本地 Embedding 或精排模型通常占数百 MB，bge-m3 等大模型可能更高。如果 VPS 已全部使用云端 api-m3 和云端 reranker，本项不会触发；若配置切回本地模型，则可能成为最大的固定内存来源。

处理建议：

- 低内存 VPS 强制使用云端 Embedding 和精排；
- 模型配置切换时显式释放旧实例；
- 本地模型缓存最多保留一个当前实例；
- 日志记录模型加载前后 RSS，便于区分模型权重与业务数据占用。

### 6.7. 管理巡检

位置：src/services/db_inspect.py 第 204-268、302-369 行；src/api/routes/db_admin.py 第 31-98 行。

Chroma 管理页带文件名筛选、正文筛选或排序时，一次最多读取 CHROMA_SCAN_CAP 指定的 2 万条正文和 metadata，再在 Python 内存中过滤、排序和分页。

BM25 管理页的问题更重。bm25_indexes 为了统计条目数会先 pickle.load 一次，又调用 BM25Index.load_or_new 再加载一次。bm25_docs 每个请求都反序列化完整索引，并为全部 chunk 构造包含正文和 metadata 的 rows 列表，最后才分页。

这些入口需要管理员权限，但它们与聊天服务运行在同一进程。管理页的短时峰值可能挤掉正在运行的请求。

处理建议：

- Chroma 筛选分批扫描，默认上限降低到实际分页需要的数量；
- 列表只读取 metadata 和正文摘要，完整正文只在三级详情读取；
- BM25 文件增加独立的轻量 manifest，列表不再反序列化索引；
- BM25 文档浏览改为独立离线工具，或使用可分页的持久化结构。

### 6.8. 聊天附件

位置：frontend/src/components/chat/Composer.tsx 第 191-254 行；src/api/schemas/chat.py 第 8-21 行。

文本附件在浏览器中通过 file.text 读取完整正文。发送时 buildMessage 又把附件正文拼入新的消息字符串，useChat 还会把完整 rawContent 保存在消息状态中。后端 ChatRequest.message 只有最小长度限制，没有最大字节数限制。

因此，一个大文本附件可能同时以 File、textContent、发送字符串、rawContent、HTTP 请求体和后端字符串等多种形式存在。前端显示的 token 估算只是提示，不会阻止发送。

处理建议：

- 前端限制单文件大小、文件数量和附件总大小；
- 后端为 ChatRequest.message 设置最大字节数，不能只依赖前端；
- 大附件改为独立上传并传文件引用，不内嵌进聊天消息；
- 发送完成后及时清除 textContent 和不再需要的 rawContent。

## 7. P2问题

### 7.1. L2无分页

位置：src/rag/ingest.py 第 424-535 行；src/api/routes/kb.py 第 123-135 行；frontend/src/components/kb/KnowledgeBaseView.tsx 第 279-282 行。

L2 已不再读取正文，但每次请求仍扫描 collection 的全部 chunk metadata，并按 doc_id 写入 grouped 字典。返回前 sorted 会再创建完整列表，随后 Pydantic 模型和 JSON 序列化还会产生额外对象。前端也一次保存全部文档，只在浏览器侧分页。

数千篇文档时通常可以接受；数万篇文档时，扫描时间和内存都会明显增长。

处理建议：建立文档级索引表，在入库和删除时增量维护 chunks、total_chars 和 ingested_at；列表 API 基于该表做服务端分页和筛选。

### 7.2. 并发放大

位置：src/config.py 第 481-499 行；src/api/routes/chat.py 第 57-60、420-443 行；src/agent/core/research_engine.py 第 242-365 行。

MAX_CONCURRENT_AGENT_RUNS 默认允许四路 Agent 同时运行。每路都会持有历史、当前 messages、工具结果、模型响应和 trace。深度研究又可在一路内部并行三个子代理，每个子代理都有独立 messages 和网页正文。

各项单独都有轮次或来源上限，但组合后的峰值约为“Agent 并发数 × 子代理并行数 × 单代理上下文”。低内存 VPS 不适合直接沿用默认值。

处理建议：按 VPS 实测内存把普通聊天并发先降为 1-2；深度研究使用单独信号量，并把并行子代理设为 1-2。

### 7.3. 前端流式

位置：frontend/src/hooks/useChat.ts 第 145-206 行；frontend/src/components/chat/MessageBubble.tsx 第 314-317 行。

每个 token_chunk 都会调用 setMessages，复制 messages 数组和当前助手消息，再用 m.content + 新片段创建增长后的字符串。Markdown 组件还会重复解析整段已生成正文。thinking_chunk 也会遍历 timeline 并拼接字符串。

这不是长期泄漏，但长回答会制造大量短生命周期对象，增加垃圾回收和浏览器堆峰值。

处理建议：先把流式片段写入 ref，每个动画帧或每 30-50 ms 合并更新一次；流式阶段使用轻量纯文本，结束后再解析 Markdown。

### 7.4. Skill正文

位置：src/agent/core/history_manager.py 第 42-99 行；src/agent/core/tool_call_engine.py 第 215-234 行；src/agent/agent.py 第 546-567 行。

load_skill 的工具结果包含完整 Skill 正文，并写入会话消息表。HistoryManager 为避免产生孤立 tool 消息，会保护含 skill_content 的助手和工具消息组，使它们即使位于普通轮次窗口之外也可能被重新加入历史。

进程级 Agent 的 system_prompt 还可能在多次 Skill 激活时持续追加正文。Skill 数量和单个正文都没有统一的总字符上限。

处理建议：会话历史只保存 Skill 名称、版本和哈希；正文按需从磁盘或缓存读取；每轮根据激活集合重建 Skill 注入块，并设置总字符上限。

### 7.5. 语义缓存

位置：src/stores/semantic_cache.py 第 61-133 行。

语义缓存把完整答案写入 Chroma documents。条目有 7 天有效期，但过期记录只在恰好被 lookup 命中时删除，没有定时清理，也没有每用户或全局容量上限。

长期运行且知识库不变化时，过期和未命中的条目会继续保留。它们主要增长磁盘，但 Chroma 的索引和缓存也会增加进程内存。

处理建议：增加周期性过期清理、每用户条数上限、全局容量上限和单答案长度上限。

### 7.6. 统计导出

位置：src/stores/trace_store.py 第 183-217 行；src/api/routes/usage.py 第 262、368 行。

Trace 概览先 fetchall 读取时间范围内全部记录，再在 Python 中排序计算 p50 和 p95。用量 CSV 导出固定读取最多 10 万行，并在 StringIO 中一次构造完整 CSV 字符串后返回。

高调用量时，这两个入口会产生数十 MB级临时对象。

处理建议：平均值和计数改为 SQL 聚合；分位数使用数据库扩展、分桶近似或采样；CSV 改为 StreamingResponse 分批读取和输出。

### 7.7. Chroma客户端

位置：src/rag/retriever.py 第 120-132 行；src/rag/ingest.py 第 283-365、409-421、538-564 行。

检索和知识库列表各自维护 PersistentClient，入库和删除还会临时创建新客户端。同一数据库路径存在多套客户端，可能重复持有 SQLite 连接、HNSW 句柄和内部缓存。

Chroma 不同版本的内部缓存行为不同，因此无法仅凭源码准确量化，但统一客户端可以减少重复资源并简化生命周期。

处理建议：所有读写路径复用一个进程级客户端，在进程关闭时统一释放。

### 7.8. 前端堆积

位置：frontend/src/components/chat/Composer.tsx 第 191-214、262-264 行；frontend/src/hooks/useChat.ts 第 439-572 行。

图片附件创建 Object URL（对象地址）后，只在手动移除或发送时调用 revokeObjectURL。切换页面、卸载 Composer 或切换会话时没有统一清理，浏览器可能继续持有 Blob。

同一助手回答每次重新生成都会把完整 content、timeline 和 plan 保存进 versions，版本数量没有上限。反复重新生成长报告时，内存按版本数增长。

处理建议：

- Composer 卸载和切换会话时释放全部 Object URL；
- versions 最多保留最近 3-5 个；
- 旧版本只保存正文和必要元数据，不保存完整工具时间线。

## 8. 条件问题

以下问题不计入 17 项主清单，但在特定配置下需要注意。

### 8.1. Thinking累积

位置：src/agent/core/tool_call_engine.py 第 98-106 行；src/llm/openai_provider.py 第 179-251 行。

开启 thinking 后，多轮工具调用会把 reasoning_content 追加到本轮 messages。流式模型调用还会在 reasoning_parts 中保存完整推理文本。轮次有硬上限，但单轮 thinking 预算可很大，长工具链可能达到数 MB甚至更高。

若线上开启高 thinking_budget，建议只保留提供商协议真正需要的最近一轮 reasoning，或为累计 reasoning 设置字符上限。

### 8.2. 非默认Agent

位置：src/api/deps.py 第 50-77 行；src/agent/autogpt_agent.py 第 273-286 行；src/agent/langchain_agent.py 第 233-236 行。

默认 PYTHON 实现已经把事件总线、session_id 和运行状态放到单次 run 中。LANGCHAIN 和 AUTOGPT 实现仍共享部分可变实例状态，多用户并发时可能发生事件串台和状态覆盖。

这首先是正确性问题，也会让异常运行保留错误上下文。生产环境应继续使用 IMP_METHOD=PYTHON，直到另外两种实现完成每次请求状态隔离。

### 8.3. 计划映射

位置：src/stores/learning_plan_store.py 第 464-516 行。

_loaded_by_session 是进程级字典。mark_loaded 会写入 session_id 到 plan_id 的映射，但删除会话时没有调用 clear_loaded。单项很小，只有长期运行并创建大量不同 session 才会明显增长。

建议在删除或清空会话时同步清除映射，或把映射改为有容量上限的缓存。

## 9. 已有边界

以下位置已经有有效上限，不是本轮首要问题：

- L2 列表只读 metadata，并按 256 条分批；
- Chroma Embedding 每批写入 16 个 chunk；
- Web 单文件上传默认上限 10 MB；
- 检索返回 top_k 最大 10，精排候选受倍数限制；
- query 改写缓存每项最大 256 条，query 向量缓存最大 512 条；
- Agent 默认历史先取最近 160 条，再保留最近 20 轮；
- Agent 工具轮次、总轮次和硬轮次均有上限；
- 单轮并行工具最多 4 个；
- 深度研究的子问题数、并行数、轮次和来源总数均有上限；
- Golden 出题上限为 20；
- 日志使用 5 MB轮转并保留 3 份；
- 前端已对主要 SSE 请求使用 AbortController；
- 评估轮询、事件监听器和大部分 Object URL 已有卸载清理。

这些边界不能抵消 BM25 常驻、全量输入和并发乘法问题，但可以避免把已经受控的路径重复列为首要修复项。

## 10. 处理顺序

### 10.1. 第一阶段

先用配置和输入限制降低 OOM 风险：

1. 记录 VPS 空闲、首次打开知识库、首次检索和单文件入库前后的 RSS；
2. 统计 BM25 pickle 大小，并对比关闭 BM25 前后的检索内存；
3. 把 MAX_CONCURRENT_AGENT_RUNS 和深度研究并行数降到符合 VPS 容量的值；
4. 给 fetch_url、备份还原、聊天附件和 ChatRequest 增加字节上限；
5. 为 SSE 队列增加容量上限和 token 合并。

### 10.2. 第二阶段

改造会随数据规模增长的全量路径：

1. 会话消息和知识库文档列表改为服务端分页；
2. 入库改为流式解析、分块和写入；
3. Chroma、BM25 管理巡检不再批量读取正文；
4. 统计和 CSV 导出改为数据库聚合或流式输出；
5. 统一 Chroma 客户端。

### 10.3. 第三阶段

减少长期常驻和缓慢堆积：

1. BM25 改为磁盘倒排或按需加载；
2. 本地模型缓存限制为当前模型；
3. 语义缓存增加定期清理和容量上限；
4. Skill 正文从会话历史中移出；
5. 前端限制回答版本数，并补齐 Object URL 清理。

## 11. 验证方法

修复前先建立基线。每个场景至少记录执行前、峰值和结束后 60 秒的 RSS，避免把 Python 内存分配器未立即归还给操作系统误判为泄漏。

建议验证以下场景：

1. 冷启动后依次打开知识库一级列表和二级文档列表；
2. 首次执行同时命中 Dense 和 BM25 的知识库检索；
3. 上传接近 10 MB 上限的文本、PDF和 DOCX；
4. 连续打开长会话并向上加载历史消息；
5. 用慢速客户端消费长回答，并在生成中途断开；
6. 并发执行普通聊天和深度研究；
7. 打开 Chroma、BM25 管理巡检页并执行筛选；
8. 还原包含向量库的大备份；
9. 连续运行 24 小时，观察语义缓存、Skill、计划映射和前端版本是否持续增长。

VPS 可先使用以下命令采样进程：

```bash
watch -n 1 'ps -o pid,rss,vsz,%mem,cmd -C python'
```

如需区分 Python 堆和原生库内存，可在测试环境增加 tracemalloc，并结合 memray 或 py-spy 检查分配热点。PyTorch、ONNX Runtime、Chroma HNSW 和 SQLite 等原生库占用不会完整出现在 tracemalloc 中，最终仍以进程 RSS 为准。

## 12. 验收标准

本轮审查完成的标准：

- L2 列表不再读取全库正文，代码和测试均能定位到分批 metadata 路径；
- 所有生产目录完成静态审查，问题给出优先级、触发路径、源码位置和处理建议；
- 管理操作峰值与线上常规请求风险分开说明；
- 已有上限和清理机制单独列出，避免重复治理；
- 明确静态估算不能替代 VPS 实测。

后续修复完成的目标：

- 低内存 VPS 的知识库列表和首次检索不触发 OOM；
- 单个外部输入、上传文件、消息和备份都有后端字节上限；
- 会话、知识库和管理列表不再依赖全量正文或全量历史；
- 流式队列、模型缓存、BM25 索引和语义缓存都有明确容量边界；
- 并发值来自实测内存预算，而不是沿用默认配置。

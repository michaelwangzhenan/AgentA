# 4. 结构设计
## 4.1. README 的读者

本项目本质是**个人作品集**，不追求做成活跃开源产品。读者优先级：

| 优先级 | 读者 | 为什么来 | 最关心 | 停留 |
|---|---|---|---|---|
| **第一** | 技术评估读者 | 从 GitHub 链接过来，快速评估项目水平 | 项目难度、工程素养、亮点是否真实 | 30 秒扫，决定要不要细看 |
| 第二 | 技术同行 / 学习者 | 搜 RAG / Agent 实现，想参考思路 | 架构怎么设计、哪些是原创、能不能看懂 | 几分钟，会点进 `design.md` |
| 次要 | 潜在使用者 | 想跑起来当私有知识库用 | 怎么装、怎么配、能不能跑通 | 到"快速开始"即够 |

**定调**：整体调性和信息排序服务于第一读者（技术评估读者）；技术同行靠"架构 + 文档导读"承接。使用者与未来维护者不单列，靠"快速开始 / 文档导读 / 命令区"自然兼顾，不为其重构结构。

## 4.2. README 要展示什么

**判定标准**：能帮评估读者在 30 秒内建立"难度 + 亮点 + 真实性 + 工程素养"印象的 → 必须展示且靠前；纯操作细节（怎么配、怎么跑）→ 使用者向，保留但折叠/靠后。

| 类别 | 内容 | 处理 |
|---|---|---|
| 必须·靠前 | 一句话定位（从零实现 · 本地私有知识库 Agent） | 顶部第一屏 |
| 必须·靠前 | 演示截图 / GIF | 真实性证据，比文字有说服力 |
| 必须·靠前 | 核心亮点扫读段 | 顶部先给一段/一行式亮点，供 30 秒扫读 |
| 必须 | 核心能力详细表格 | 承接扫读段，靠后展开 |
| 必须·靠前 | 架构图 | 一眼看出设计能力 |
| 必须 | 工程化质量（测试 / 评估 / CI 三道门） | 区分"跑通 demo"与"生产级素养"，评估读者尤其看重 |
| 保留·靠后 | 快速开始（装 / 配 / 启动） | 使用者向 |
| 去掉 | 主要配置（.env 大块） | 与 `.env.example` 冗余；快速开始里一句"配置见 `.env.example`"带过 |
| 保留·折叠 | 实用工具命令区 | `<details>` 折叠，侧面证明有配套工具链 |
| 保留·强调 | 文档导读 | 承接技术同行；突出"8 轮迭代 + `design.md`"作为深度设计信号 |

**去掉**：原"项目数据一览"（代码量 / 文档行数 / 测试数等量化表）。理由——态势数字易过时，且专门堆一张"数据表"显刻意；量化信息改为分散融进亮点段与工程化质量节里自然呈现。

**叙述口吻（重要）**：README 里所有能力/亮点写的都是 **AgentA（产品）能做什么**，不直接写作者能力。评估读者是通过产品的难度反推作者水平——产品能力是作者能力的证据。因此统一用**纯产品视角客观陈述**（"AgentA 支持 X / 集成 Y"），靠内容本身难度说话，不用"我实现了…""从零手写"这类自夸口吻。

## 4.3. 目标结构

**排布逻辑**：倒金字塔——最能打动评估读者的（定位 / 演示 / 亮点 / 架构）全放前半屏，操作细节沉底。

| # | 章节 | 内容 | 服务读者 |
|---|---|---|---|
| — | 标题 + badges | 项目名 + 状态徽章 | 全部 |
| 1 | 一句话定位 + 演示 | 定位句 + 截图 / GIF | 评估读者（30 秒建立"是什么 + 真实"） |
| 2 | 核心亮点扫读段 | 一段 / bullet 式硬核点罗列 | 评估读者（扫读） |
| 3 | 整体架构图 | mermaid 架构图 | 评估读者 + 同行 |
| 4 | 核心能力 | RAG / Agent / 交互 / 3 套实现详细表格 | 同行 |
| 5 | 工程化质量 | 测试 / 评估 / CI 三道门 | 评估读者（生产级素养） |
| 6 | 快速开始 | 装 / 配（一句带 `.env.example`）/ 启动 | 使用者 |
| 7 | 实用工具（折叠） | rag_cli / eval 命令 | 使用者 / 维护者 |
| 8 | 文档导读（强调） | 8 轮迭代 + `design.md` 引流 | 同行（深度信号） |

**badge 设计**：去掉计数型徽章（Tests 46 files、Code 27K LOC 等）——与"去掉数据一览"同理，态势数字易过时。只留稳定徽章：CI 状态 / Python 版本 / License 等。

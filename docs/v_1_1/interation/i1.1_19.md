# 1. 背景
agenta v1.1 已经开发完毕（参考 docs/ 下迭代历史）

根据 [guest 账号](./i1.1_17_guest.md) 的设计，现在有一个 read only 的 guest 账号，用于让用户进行体验。
但是新建的guest账号里的内容都是空的，为了更好的展示，需要让用户点“立即体验”后，进入应用时能看到尽量完整的功能。
做法是把 guest 临时提权到 user，手工填写或生成下面的内容，灌完再把角色回落到 readonly。i1.1_17_guest.md 第 2.4 节要求 guest 长期固定为 readonly，这里的提权只是灌数据期间的临时操作，不改变那条约定。

# 2. 为 guest 生成完整信息

访客的主要预期对象是招聘方（HR 与技术面试官），所以每一节填什么的判断标准是：招聘方看了对我求职有利。

内容分两路。我的真实经历已经入了知识库，只通过 2.6 的问答检索出来，访客问一句看一句，比直接摊开一份简历更能看出检索质量。其余各节（记忆、rules、学而时习、用量看板）填的是这个演示账号的使用痕迹，作用是把 AgentA 的功能展示完整，不承载简历内容。两路合起来，访客走完一圈既体验了产品，也了解了我。

## 2.1. 角色设定

guest 是一个后端与 AI 方向的技术人，用 AgentA 做资料问答和技术调研；他的知识库里有我的简历与项目说明。记忆、rules、学而时习、用量看板都是这个用户留下的使用痕迹。

不把他设定成招聘方：访客可能是 HR，也可能是同行或潜在合作方，写成通用技术人谁看都不违和。招聘方视角只作为内容取舍标准用（见下节），不写进账号身份。

分工要分清，这是后面各节不跑偏的前提：

- 我的真实经历只放在知识库，靠 2.6 的问答检索出来，不往记忆和 rules 里塞
- 记忆、rules、学而时习、用量看板展示的是 AgentA 的功能本身，内容围绕「这个用户怎么用 AgentA」来编

agent 讲我的经历时用第三人称（他做过什么），像个招聘助手；不做第一人称数字分身，免得访客分不清在说话的是谁。

### 2.1.1. 内容取舍标准

招聘方想确认五件事：能干什么、做过什么、怎么干的、学得动不动、靠不靠谱。前两件由知识库问答直接回答（2.6）；后三件靠使用痕迹侧面体现——rules 和记忆写得讲究，本身就说明这人怎么思考问题。

AgentA 本身就是我最大的作品，访客体验产品的过程就是在审这个项目。所以 2.6 的问答里要有一批「这个系统是怎么实现的」，不能全是履历题，后者更能体现技术深度。

### 2.1.2. 说话风格与边界

- 中文，先给结论再给依据，带具体数字，不堆形容词
- 讲我的经历用第三人称；讲 AgentA 实现时用中立技术口吻
- 知识库里查不到就直说，不补推测
- 不谈薪资、联系方式等私人信息，引导到联系页
- 不评价前雇主与同事

### 2.1.3. 只读与升档

guest 固定只读，访客看到的问答是提前跑好存下来的会话（见 2.6），不是现场对话——chat 的写权限最低是 user（src/api/permissions.py 的 SCOPE_MIN_ROLE）。有兴趣的访客可以申请 user 账号做真实问答，需要时再开 admin。这与 i1.1_17_guest.md 第 2.4 节一致：写体验走独立账号，不动 guest 角色。

## 2.2. 记忆

这一节展示的是 AgentA 的记忆功能，不放我的简历。要让访客看懂三件事：记忆从哪来、长什么样、怎么影响后面的回答。

### 2.2.1. 放什么

选条目的标准：每条要么能在 2.6 的会话里看出它是怎么学到的，要么能在后续回答里看出它起了作用。只是躺在页面上好看的条目不要。

三种来源都要有实例，取值见 src/stores/user_memory.py 的 MEMORY_SOURCES，页面上分别显示自动、请记住、手工。

请记住（explicit）两条，这两条最能演示因果，访客能在后面的回答里直接看到效果：

- 用户要求回答先给结论再给依据，控制在 200 字以内
- 用户要求涉及资料内容的回答标出知识库出处，不要泛泛而谈

自动（auto）五条，看起来像从对话里自然学到的：

- 用户是后端工程师，主要用 Python 与 FastAPI，前端用 React
- 用户在做企业内部知识库项目，关注 RAG 与 Agent 方向
- 用户看重工程落地与线上稳定性，对论文和刷题类内容不感兴趣
- 用户多次问到 token 成本与响应延迟，关心线上开销
- 用户习惯中文提问，技术名词保留英文原文

手工（manual）三条，用户自己敲进去的硬性约束：

- 评估检索效果时优先看命中率与 MRR（Mean Reciprocal Rank，平均倒数排名），不看主观感受
- 部署环境是单机 Docker、无 GPU，选型要考虑这个约束
- 长文档优先按标题层级切分，不用固定长度切

一共十条，落在 8 到 12 条这个区间：太少看不出功能，太多页面显得杂乱。这批条目会注入 system prompt，「看重工程落地」之类的偏好会让 2.6 里的回答自然偏向工程细节，正是想要的方向。

### 2.2.2. 怎么放进去

写个脚本调 POST /api/memory 灌进去。请求体是 text 与 source，source 可以直接指定三种取值中的任意一个（见 src/api/schemas/memory.py 的 MemoryCreateRequest），所以不需要真跑对话去等 LLM 自动提取。鉴权走 cookie，脚本先 POST /api/auth/login，之后复用同一个 HTTP 会话即可。

前置条件三条：

- guest 临时提权到 user。memory 的写权限最低是 user，否则接口返回 403
- 确认 USER_MEMORY_ENABLED=true，否则接口返回 503
- 灌完立刻把 guest 降回 readonly

这条路省事，但有个破绽要补：伪造的 auto 条目在会话里找不到出处，十条的创建时间还会挤在同一分钟。补救办法是让 2.6 的会话话题跟这批记忆对得上——访客看到记忆里写「关心 token 成本」，会话里确实有几轮在问成本，就不会觉得突兀。所以 2.6 的会话脚本要照着这十条来设计，两节必须配套。

## 2.3. rules

rules 是一整块 Markdown 文本（不是条目列表），上限 4000 字符，每轮对话包成 user_rules 块注入 system prompt。写权限用的是 memory 这个 scope，不是单独的 rules scope。

它和记忆的分工要划清，两边别写重复的话：rules 写「怎么干活」——知识库里有什么、什么时候查、怎么引用；记忆写「用户是谁、有什么临时偏好」。

rules 还有个记忆没有的作用：基础 system prompt 明确写了何时调 search_knowledge 以 user_rules 为准（src/agent/core/agent_commons.py 的工具策略一节）。所以这块写好了，2.6 里问答的检索质量是真的会提升，不只是摆在页面上给人看。

### 2.3.1. 知识库现状

主集合 kb_m3 有 93 篇文档，写 rules 前先认清里面有什么：

- 个人资料：resume_cn.docx、capability.md、daily_work.md、AgentA.pptx，以及 8 篇项目说明（BB_Pooling、Beamforming、MIMO、Parallel_Scheduling、Load_Control、edgeAI_MuPairing、edgeAI_ScellAct、SaS）
- 3GPP 5G 规范：38xxx 与 37xxx 系列英文文档，体量最大，例如 38331 RRC 有 6349 个分片、38133 有 7805 个
- 5G 中文技术笔记：BWP、CA、CSI、MIMO、URLLC、SRS、DSS 等 14 篇
- C++ 与编码规范：C++11/14/17 系列、Cmake、并发、网络编程、5G C++ Coding Guidelines、clean code 系列
- AI 学习资料：1_AI 到 10_Usage 共 10 篇

### 2.3.2. rules 正文

下面这段直接粘进 Rules 页：

```markdown
## 知识库说明

本库有五类资料：

1. 个人资料：resume_cn.docx（简历）、capability.md（能力清单）、daily_work.md、
   AgentA.pptx，以及 *_project.md 若干（BB_Pooling、Beamforming、MIMO、
   Parallel_Scheduling、Load_Control、edgeAI_MuPairing、edgeAI_ScellAct、SaS）
2. 3GPP 5G 规范：38xxx / 37xxx 系列英文文档（RRC 38331、MAC 38321、RLC 38322、
   PDCP 38323、物理层 38211 / 38212 / 38213 / 38214 等）
3. 5G 中文技术笔记：BWP、CA、CSI、MIMO、URLLC、SRS、DSS 等
4. C++ 与编码规范：C++11/14/17、Cmake、并发、网络编程、5G C++ Coding Guidelines
5. AI 学习资料：机器学习、NLP、Agent、强化学习、数学基础等

## 什么时候查库

- 问经历、项目、技能：必查，优先第 1 类
- 问 5G 协议细节、参数、流程：必查第 2 类，第 3 类作辅助解释
- 问 C++ 用法或编码规范：查第 4 类
- 纯闲聊或与本库无关的常识：不用查

## 检索要求

- 先术语化再检索：载波聚合用 CA、带宽部分用 BWP、信道状态信息用 CSI
- 3GPP 文档是英文，中文提问时中英文关键词一起检索
- top_k 用默认 8，不要传 1 到 2
- 命中分数低于 0.5 算弱命中，换关键词重试一次再下结论

## 回答规范

- 中文回答，技术名词与规范编号保留英文原文（如 RRC 38331、PDCP）
- 涉及本库内容的结论必须标出处，给到文件名，能定位章节就给章节
- 查不到就说查不到，不要用通用知识顶替，更不要编造规范条款
- 讲项目时说清背景、做了什么、结果如何，不堆形容词

## 边界

- 不谈薪资、联系方式等私人信息，需要联系时引导到联系页
- 不评价前雇主与同事
```

### 2.3.3. 怎么放进去

跟记忆用同一个脚本，调 PUT /api/rules 写入，请求体只有 text 一个字段。超过 4000 字符会返回 400。写权限同样是 memory scope，所以照样要先把 guest 提权到 user，写完降回 readonly。

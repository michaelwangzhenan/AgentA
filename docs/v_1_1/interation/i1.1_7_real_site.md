5. EVAL_AUTO_GOLDEN_MAX_Q 改成 EVAL_GOLDEN_MAX_Q 只作 默认出题数量。

### 3.2.4. 优化golden 集策略与实现

全局共用 rag_golden.db，不为每个 collection（如 api-m3、zh）各建一套独立的 golden 库。
评估对全库检索（贴近真实用户混库提问）。
两主题（简历/3gpp）用 type 标签切片分析，不改表结构。

总数量：100
主题配比：personal 25–35% · 3GPP 50–60% · project 15–25%。
单文档出题数：每 1K 一题，不超过 EVAL_GOLDEN_MAX_Q / UI设定
大/小文件策略： <6K, 全文一次 LLM，max_q 题全在这一轮出; >6K, 滑动窗口分段，每段单独调 LLM
题数分配（总题数 = compute_golden_max_q 的结果）：
每段题数 = max(1, max_q // 段数)   # 余数分给前几段

**数据结构（不改 schema）**


| 字段                         | 约定                 |
| -------------------------- | ------------------ |
| `query`                    | 必填，模拟真实问法          |
| `expected_keywords`        | 强烈建议，2–4 个术语/实体    |
| `expected_source_contains` | 强烈建议，文件名或 spec 号片段 |
| `expected_source`          | 一般不用（路径易变）         |
| `type`                     | 主题标签，评估不参与，供切片     |
| `note`                     | 人工备注               |
| `doc_id`                   | AI 生成绑文档；综合题留空     |


`type` 枚举：`personal-bio` · `personal-project` · `3gpp-def` · `3gpp-proc` · `3gpp-param` · `project-impl`（AI 出题 / 审核时填写，3.2.5 可让 LLM 自动带 `type`）。

最小可用：`query` + (`expected_keywords` 或 `expected_source_contains`)。

### 3.2.7. 大文件上传 HTTP 413（nginx 请求体上限）

#### 现象（2026-07-13 线上实测）

批量文件夹入库 `5G_38_series_RL16/`（25 个 docx）时：

- 失败文件：`23501-g51_System architecture for the 5G System (5GS).docx`
- 前端 toast：`…：HTTP 413`（无「文件过大（X MB > 10 MB）」等中文 detail）
- 同批次小文件可成功，例如 `38101-4-…Performance requirements.docx`（818 KB）正常入库 526 块
- 批次**不中断**：单文件失败计入「失败」，继续传下一个

#### 根因

| 层 | 上限 | 超限表现 |
|---|---|---|
| **nginx**（`client_max_body_size` 默认 **1 MB**） | 1 MB | 反代层直接 413；**uvicorn 访问日志无该 POST**；响应体通常非 JSON |
| **后端**（`WEB_MAX_UPLOAD_MB`，默认 10） | 10 MB | `kb.py` 返回 413 + `detail` 中文说明；uvicorn 有 `POST /api/kb/upload` 413 |

部署文档 `i1.1_3_deploy.md` 9.3 的 nginx 配置**未设** `client_max_body_size`，与 UI 文案「单文件 ≤ 10 MB」、后端 `WEB_MAX_UPLOAD_MB=10` **不一致**。实测失败更符合 nginx 1 MB 拦截（toast 裸 `HTTP 413` + 日志无对应请求）。

前端 `DropZone` 仅展示 10 MB 提示，**上传前不做大小校验**，大文件会直接发到服务器。

#### 排查

```bash
# VPS：确认 nginx 是否限制请求体
grep client_max_body /etc/nginx/sites-available/agenta

# nginx 侧常见报错
sudo tail -30 /var/log/nginx/error.log
# → client intended to send too large body

# 本地：看失败文件实际大小
ls -lh "5G_38_series_RL16/23501-g51_System architecture for the 5G System (5GS).docx"
```

区分 nginx vs 后端：若 `uvicorn.log` **没有**该文件的 `POST /api/kb/upload`，且 toast 只有 `HTTP 413` → nginx；若有 413 且 detail 含「文件过大」→ 后端 10 MB 上限。

#### 修改方法

**1. nginx（必做，与 `WEB_MAX_UPLOAD_MB` 对齐）**

在 `server` 或 `location /api/` 增加：

```nginx
client_max_body_size 10m;
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

同步更新 `i1.1_3_deploy.md` 9.3 模板，避免新环境再踩坑。

**2. 按文件大小分支处理**

| 大小 | 处理 |
|---|---|
| ≤ 1 MB | 修 nginx 前即可过 nginx；修后正常 |
| 1–10 MB | 修 nginx 后应可入库 |
| > 10 MB | 需提高 `WEB_MAX_UPLOAD_MB`（及 nginx 同值），或压缩/拆分文档 |

**3. 前端体验（可选，本阶段可后做）**

- 选文件后按 `WEB_MAX_UPLOAD_MB`（或配置接口下发值）预检，超限直接标红、不发送请求
- 批量失败时展示后端 `detail`，避免只显示 `HTTP 413`

**4. 修完后的操作**

nginx 生效后，对失败文件**单独重传**（批次不会自动重试失败项）。

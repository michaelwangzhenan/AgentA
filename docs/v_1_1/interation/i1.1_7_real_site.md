## 3.2. 入库优化
### 3.2.1. 默认入库模型设为 api-m3

UI 入库下拉默认选中 `api-m3`（跟随 `EMBEDDING_MODEL`）。

- `GET /api/kb/collections` 新增 `default_ingest_alias` 字段
- 前端入库面板用该字段初始化下拉，不再从 `is_default` 库的 alias 推断（api-m3 时否则会落到 m3）
- `.env` / `.env.example`：`EMBEDDING_MODEL=api-m3`

### 3.2.2. 入库时生成 golden 的LLM 可选

1. 在入库目标库下拉旁加 「评估题 LLM」，默认：不生成，可选： kimi2.5 和 DeepSeek V4 Flash， 仅 admin 可见
2. EVAL_AUTO_GOLDEN_ENABLED 改成 EVAL_GOLDEN_LLM，对应上面3个可选值，可在 3.2.3 复用，默认为 None
3. 在入库目标库下拉旁加 “生成Golden数量”，
4. UI 系统配置-评估 页，删除 RAG_GOLDEN_DB_PATH，EVAL_AUTO_GOLDEN_ENABLED， EVAL_AUTO_GOLDEN_MAX_Q 三项配置
5. EVAL_AUTO_GOLDEN_MAX_Q 改成 EVAL_GOLDEN_MAX_Q 只作 默认出题数量。
6. 实现时考虑后面3.2.3 和 3.2.6 的可复用性

### 3.2.3. 生成 golden 可选 LLM
知识库 L2 点「生成评估」按钮时，增加可选生成 golden 的 LLM 和 生成数量


### 3.2.4. 优化golden 集策略与实现

全局共用 rag_golden.db，不为每个 collection（如 api-m3、zh）各建一套独立的 golden 库。
评估对全库检索（贴近真实用户混库提问）。
两主题（简历/3gpp）用 type 标签切片分析，不改表结构。

总数量：100
主题配比：personal 25–35% · 3GPP 50–60% · project 15–25%。
单文档出题数：每 1K 一题，不超过 EVAL_GOLDEN_MAX_Q / UI设定
大/小文件策略： <6K, 全文一次 LLM，max_q 题全在这一轮出; >6K, 滑动窗口分段，每段单独调 LLM
题数分配（总题数 = compute_golden_max_q 的结果）：
每段题数 = max(1, max_q // 段数)   # 余数分给前几段


**数据结构（不改 schema）**

| 字段 | 约定 |
|------|------|
| `query` | 必填，模拟真实问法 |
| `expected_keywords` | 强烈建议，2–4 个术语/实体 |
| `expected_source_contains` | 强烈建议，文件名或 spec 号片段 |
| `expected_source` | 一般不用（路径易变） |
| `type` | 主题标签，评估不参与，供切片 |
| `note` | 人工备注 |
| `doc_id` | AI 生成绑文档；综合题留空 |

`type` 枚举：`personal-bio` · `personal-project` · `3gpp-def` · `3gpp-proc` · `3gpp-param` · `project-impl`（AI 出题 / 审核时填写，3.2.5 可让 LLM 自动带 `type`）。

最小可用：`query` + (`expected_keywords` 或 `expected_source_contains`)。

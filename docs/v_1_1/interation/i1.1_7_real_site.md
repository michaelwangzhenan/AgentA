## 3.2. 入库优化

### 3.2.1. 默认入库模型

UI 入库下拉默认选中 api-m3（跟随 EMBEDDING_MODEL）。

- GET /api/kb/collections 新增 default_ingest_alias 字段
- 前端入库面板用该字段初始化下拉，不再从 is_default 库的 alias 推断（api-m3 时否则会落到 m3）
- .env / .env.example：EMBEDDING_MODEL=api-m3

### 3.2.2. 入库 golden LLM

1. 在入库目标库下拉旁加「评估题 LLM」，默认：不生成，可选：kimi2.5 和 DeepSeek V4 Flash，仅 admin 可见
2. EVAL_AUTO_GOLDEN_ENABLED 改成 EVAL_GOLDEN_LLM，对应上面 3 个可选值，可在 3.2.3 复用，默认为 None
3. 在入库目标库下拉旁加「生成 Golden 数量」
4. UI 系统配置-评估页，删除 RAG_GOLDEN_DB_PATH、EVAL_AUTO_GOLDEN_ENABLED、EVAL_AUTO_GOLDEN_MAX_Q 三项配置
5. EVAL_AUTO_GOLDEN_MAX_Q 改成 EVAL_GOLDEN_MAX_Q，只作默认出题数量
6. 实现时考虑后面 3.2.3 和 3.2.6 的可复用性

### 3.2.3. L2 生成 golden

知识库 L2 点「生成评估」按钮时，增加可选生成 golden 的 LLM 和生成数量。

### 3.2.4. golden 策略

全局共用 rag_golden.db，不为每个 collection（如 api-m3、zh）各建一套独立的 golden 库。
评估对全库检索（贴近真实用户混库提问）。
两主题（简历/3GPP）用 type 标签切片分析，不改表结构。

总数量：100。
主题配比：personal 25–35%、3GPP 50–60%、project 15–25%。
单文档出题数：每 1K 一题，不超过 EVAL_GOLDEN_MAX_Q / UI 设定。
大/小文件策略：小于 6K 全文一次 LLM，max_q 题全在这一轮出；大于 6K 滑动窗口分段，每段单独调 LLM。

题数分配（总题数 = compute_golden_max_q 的结果）：

```
每段题数 = max(1, max_q // 段数)   # 余数分给前几段
```

数据结构: 不改 schema，字段约定如下：

| 字段 | 约定 |
| --- | --- |
| `query` | 必填，模拟真实问法 |
| `expected_keywords` | 强烈建议，2–4 个术语/实体 |
| `expected_source_contains` | 强烈建议，文件名或 spec 号片段 |
| `expected_source` | 一般不用（路径易变） |
| `type` | 主题标签，评估不参与，供切片 |
| `note` | 人工备注 |
| `doc_id` | AI 生成绑文档；综合题留空 |

type 枚举：personal-bio、personal-project、3gpp-def、3gpp-proc、3gpp-param、project-impl（AI 出题/审核时填写，3.2.5 可让 LLM 自动带 type）。

最小可用：query +（expected_keywords 或 expected_source_contains）。

### 3.2.7. 大文件 HTTP 413

现象：批量文件夹入库 5G_38_series_RL16/（25 个 docx）时：
- 失败文件：23501-g51_System architecture for the 5G System (5GS).docx
- 前端 toast：…：HTTP 413（无「文件过大（X MB > 10 MB）」等中文 detail）
- 同批次小文件可成功，例如 38101-4-…Performance requirements.docx（818 KB）正常入库 526 块
- 批次不中断：单文件失败计入「失败」，继续传下一个

根因：
nginx 的 client_max_body_size 默认 1 MB。超限时反代层直接 413；

修改方法：
在location /api/ 增加：

```nginx
client_max_body_size 10m;
```

启用：
```bash
sudo nginx -t && sudo systemctl reload nginx
```

### 3.2.8. L2 列表内存

进入知识库 L2 文档列表时 VPS 内存飙高甚至死机。

根因：list_kb_documents 一次 collection.get(include=documents) 拉全库正文。
修复：只读 metadata、256 条分批；新入库写 char_count。

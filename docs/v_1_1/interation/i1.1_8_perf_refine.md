# 性能优化

## 入库解析

- 入库前检查 DOCX 解压大小：超过流式阈值走逐段解析，仅硬上限才拒绝。
- 大文件放到独立子进程解析，限制内存和执行时间，避免拖死服务。
- 自动跳过 `~$` 开头的 Office 临时文件。
- 分块处理解析结果，减少完整文本及中间副本同时驻留内存。

设计方案：

- DOCX 在解析前统计 ZIP 解压总量：超过 16 MiB 改用流式读 word/document.xml 逐段产出；超过硬上限（默认 512 MiB）才拒绝。
- 解析放入独立子进程；Linux 设置 512 MiB 硬限制，父进程统一执行 120 秒超时和异常回收。
- 子进程把清洗后的段落写入临时流；父进程按章节增量分块，并分批写入 Chroma 和 BM25，保留现有标题路径、行号、内容哈希和总分块数字段。
- Web 上传、批量扫描和解析入口三层过滤 ~$ 临时文件。
- 三个限制作为配置项同步到 .env、.env.example、后端配置和设置界面。
- 测试覆盖硬上限拒绝、流式大文件、超时、内存超限、临时文件、标题元数据、幂等入库及批量写入。

本次实现：

- DOCX 解压超过 16 MiB 走流式逐段解析；硬上限 512 MiB；子进程内存 512 MiB，超时 120 秒。
- DOCX 解析结果按标题区段分块，通过临时文件分批写入，保留原有元数据和内容哈希。
- Web 上传、批量扫描和解析入口均过滤 Office 临时文件。
- 其他文件格式及数据库结构保持不变。

## BM25

- 不在内存中长期保存整库正文、分词结果和词频副本。
- 文件入库时增量更新，避免每次重算并写入整个索引。
- 增加从 Chroma 重建 BM25 的工具，处理索引不一致。

设计方案：

- 索引只持久化 metadata、词频和文档长度；正文检索时按 chunk id 回 Chroma 取。
- 文档频率与平均长度增量维护，入库时只更新受影响 chunk，不再全库重算。
- 批量入库结束时统一写盘一次；单文件上传在文件完成后写盘一次。
- 新增 rag_cli bm25-rebuild，从 Chroma 分批重建索引。

本次实现：

- bm25_index 升级为 v2 紧凑格式；兼容读取旧版 pkl。
- ingest_all 改为整批结束后 commit；ingest_one 单文件结束后 commit。
- retriever 的 BM25 命中回表取正文；管理端 L3 详情同样回表。
- 命令：python tools/cli/rag_cli.py bm25-rebuild -m <alias>

## 服务保护

- 限制并发入库数和单次入库资源。
- 在解析、分块、嵌入、Chroma 写入和 BM25 更新的开始、完成及异常节点记录日志。
- 日志包含文件名、文件大小、解压大小、分块数、阶段耗时、进程内存和系统可用内存。
- 关键日志立即写入文件，避免死机时仍停留在缓冲区。

设计方案：

- 新增 `INGEST_MAX_CONCURRENT`（默认 1）：Web 上传与 CLI 共用信号量，超出时排队等待。
- 新增 `src/services/ingest_telemetry.py`：`IngestProbe` 在各阶段打结构化 `[ingest]` 日志；`flush_log_handlers()` 在每条关键日志后刷盘。
- 阶段划分：`file` / `parse` / `split` / `embed` / `bm25`；`embed` 含 Chroma upsert（含 embedding），`bm25` 含 commit。
- 内存快照：Linux 读 `/proc/self/status` 与 `/proc/meminfo`；Windows 用系统 API，读不到记 `-1`。

本次实现：

- `ingest_one` / `ingest_all` 经 `ingest_slot()` 限并发；单文件 `file_start` / `file_done` / `file_error` 日志。
- `_ingest_one_file` / `_ingest_docx_file` 接入阶段日志与内存字段。
- 配置 `INGEST_MAX_CONCURRENT` 同步到 `.env`、`.env.example`、`config.py`、设置界面。

根因：BM25 索引 commit 后仍留在进程内 _index_cache，全库词频与元数据常驻（约数百 MiB）。

注意：Linux 的 available 不会立刻回到入库前——Python 分配器与页缓存可能仍占 used；但应明显高于入库刚结束时的 291Mi。盯 [ingest] BM25 已写盘并释放 日志里的 avail_mb。


# 进一步优化

来源：i1.1_8_memory.md 审查清单，扣除本文「入库解析 / BM25 / 服务保护」已落地项。BM25 入库后 release 已缓解峰值，但首次检索仍会按需从 pkl 载入整库索引；检索路径仍可能长期占用内存。

## P0

### BM25 检索常驻

- 检索命中后索引仍留在 _index_cache，大库首次检索后持续占用内存。
- 中期改为磁盘倒排或按需加载；短期可加冷索引淘汰、限制进程内常驻 collection 数量。
- 低内存 VPS 可配置关闭 BM25，与纯 Dense 基线对比。

## P1

### 网页抓取（6.2）

- fetch_url 仍整包读入响应体，max_chars 只限返回给模型的正文。
- 增加 MAX_FETCH_BYTES（建议 2–5 MB）；stream 分块读取，超限立即中止。
- Jina Reader 回退路径共用同一字节上限。

### 会话全读（6.3）

- GET /api/sessions/{id}/messages 仍 fetchall 全量消息；前端全量挂载。
- 消息 API 增加 limit 与 before_id 游标；首屏只返最近若干轮，上滚再加载。
- 消息列表窗口化渲染；历史工具结果只保留摘要，正文按需读取。

### SSE 队列（6.4）

- asyncio.Queue 无 maxsize；慢客户端断开后 Agent 仍跑，事件堆积。
- 设队列容量上限；token_chunk 按时间或字数合并入队。
- 队列满时丢弃可合并的进度事件，保留终态事件；客户端断开后协作式取消 Agent。

### 备份还原（6.5）

- 上传 zip 无大小上限；解压成员整包读入内存。
- 限制压缩包与解压后总大小；检查 ZipInfo.file_size 防异常压缩比。
- 流式解压；还原大向量库时进入维护状态，避免与聊天/入库并发。

### 本地模型（6.6）

- Embedding / CrossEncoder 缓存无淘汰，切换模型后旧实例可能残留。
- 低内存 VPS 强制云端 Embedding 与精排；切换时显式释放；缓存最多保留当前实例。

### 管理巡检（6.7）

- Chroma 筛选一次最多扫 2 万条正文；BM25 列表/浏览多次反序列化完整索引。
- Chroma 分批扫描，列表只返摘要；BM25 增加轻量 manifest，列表不再 load pkl。

### 聊天附件（6.8）

- 前端 file.text 全读，后端 ChatRequest.message 无最大字节数。
- 前后端限制单文件、数量与总大小；大附件改独立上传传引用；发送后清理 textContent。

### 入库残余（6.1 部分）

- 非 DOCX 格式、单文档 chunk 数仍缺硬上限（DOCX 流式与子进程已做）。
- 视需要把解析/分块/写入流水线推广到 PDF、TXT 等格式。

## P2

### L2 无分页（7.1）

- 仍扫描全库 metadata 并在内存聚合；前端浏览器侧分页。
- 文档级索引表 + 服务端分页与筛选。

### 并发放大（7.2）

- MAX_CONCURRENT_AGENT_RUNS 默认 4，深度研究内部仍多路并行。
- 按 VPS 实测把聊天并发降为 1–2；深度研究单独信号量，子代理并行 1–2。

### 前端流式（7.3）

- 每个 token_chunk 触发 setMessages 与整段 Markdown 重解析。
- 流式片段先写 ref，按帧或 30–50 ms 合并更新；流式阶段纯文本，结束后再 Markdown。

### Skill 正文（7.4）

- load_skill 完整正文写入会话；HistoryManager 可能保护窗口外 skill 消息组。
- 历史只存名称/版本/哈希，正文按需读取；注入块设总字符上限。

### 语义缓存（7.5）

- 过期条目仅命中时删除，无定时清理与容量上限。
- 周期性清理、每用户/全局条数上限、单答案长度上限。

### 统计导出（7.6）

- Trace 概览 fetchall 后 Python 算分位数；CSV 一次构造最多 10 万行字符串。
- 计数与均值改 SQL 聚合；分位数近似或采样；CSV 流式输出。

### Chroma 客户端（7.7）

- 检索、列表、入库/删除各自 PersistentClient，可能重复连接与缓存。
- 进程级单例客户端，关闭时统一释放。

### 前端堆积（7.8）

- 图片 Object URL 切换会话/卸载时未统一 revoke；回答 versions 无上限。
- 卸载与切会话时释放全部 Object URL；versions 保留最近 3–5 个，旧版不存完整时间线。

## 条件项（配置相关）

- Thinking 累积：高 thinking_budget 时多轮 reasoning 可能达数 MB，建议只保留协议必需最近一轮或设字符上限。
- 非默认 Agent：LANGCHAIN / AUTOGPT 共享可变状态，生产应继续 IMP_METHOD=PYTHON。
- 计划映射：删除会话时清理 _loaded_by_session，或改为有容量上限的缓存。

## 实现步骤

以下按依赖与风险排序；每步做完跑相关测试并在 1.6G VPS 上记一次 avail_mb。上文「入库解析 / BM25 / 服务保护」已完成，从步骤 1 起算。

### 步骤 1：输入字节上限（防 OOM，改动小）

1. config.py / .env.example / config_meta：新增 MAX_FETCH_BYTES（建议 4 MB）、BACKUP_MAX_UPLOAD_MB、BACKUP_MAX_UNZIP_MB、CHAT_MESSAGE_MAX_BYTES。
2. src/agent/tools.py fetch_url：stream 分块读，累计超 MAX_FETCH_BYTES 中止；Jina 回退路径同一上限。
3. src/api/routes/backup.py + runtime_backup.py：上传超 BACKUP_MAX_UPLOAD_MB 拒收；解压前累加 ZipInfo.file_size，超 BACKUP_MAX_UNZIP_MB 或压缩比异常拒收；zf.open + copyfileobj 流式写盘。
4. src/api/schemas/chat.py + 校验中间件：CHAT_MESSAGE_MAX_BYTES 超限返回 413。
5. frontend Composer / useChat：单文件、附件数量、总大小上限，与后端对齐；发送后清 textContent。
6. 测试：超限 fetch、zip 炸弹、超大 message、附件拒收。

### 步骤 2：SSE 与并发保护

1. src/api/routes/chat.py：asyncio.Queue(maxsize=N)（配置项 SSE_QUEUE_MAXSIZE）；token_chunk 缓冲合并（按 50 ms 或 512 字符 flush）。
2. 队列满：丢弃可合并的 progress/thinking_chunk，final_answer / error 必须入队或直写。
3. 客户端断开：设 cancel 标志，Agent 与 research_engine 轮询后尽早退出；断开时 drain 队列。
4. config：低内存部署文档写明 MAX_CONCURRENT_AGENT_RUNS=1～2、深度研究子代理并行 1～2（改 config 默认值或 deploy 文档示例，二选一落地）。
5. 测试：慢消费 SSE、中途 abort、四路并发不超内存预算。

### 步骤 3：BM25 检索路径释放（P0）

1. src/rag/bm25_index.py：检索用 get_index 支持 TTL 或 LRU，限制 _index_cache 最多 1 个 collection；或检索结束 N 分钟无命中后 drop_index。
2. 可选：commit_index(release=True) 已在入库路径；检索路径首次 load 后同样在无活跃查询时 release。
3. 验收：大库首次检索后完成几轮查询，rss_mb 应回落；对比 BM25_ENABLED=false 基线。
4. 中期单列任务：磁盘倒排或按 chunk 分批加载（本步不做）。

### 步骤 4：会话消息分页

1. SessionStore.load 改为 load_page(session_id, limit, before_id)；sessions 路由增加 query 参数。
2. frontend useChat：首屏只拉最近 40～80 条；MessageList 上滚触发 before_id 加载。
3. 可选同批：react-window 或等效窗口化，只挂载可见消息。
4. 工具结果：新消息只存摘要字段；历史大 tool 正文按需 API（可拆步骤 4b）。
5. 测试：千条消息会话首屏响应体与 DOM 节点数可控。

### 步骤 5：入库残余

1. config：INGEST_MAX_CHUNKS_PER_DOC（如 5000），超限拒绝或截断并打日志。
2. 评估 PDF/TXT 是否走与 DOCX 相同的分批写入；至少保证 parser → split → embed 不同时持有全量 documents 列表。
3. 测试：超大 TXT、超限 chunk 数。

### 步骤 6：管理巡检降峰

1. db_inspect Chroma：按 CHROMA_SCAN_CAP 分批 get，列表只返正文前 200 字摘要；三级详情才取全文。
2. bm25_index 写盘时同步写 manifest.json（collection、doc 数、文件 mtime）；bm25_indexes / bm25_docs 列表读 manifest，不再 pickle.load 全索引。
3. 测试：2 万条筛选请求峰值内存与响应时间。

### 步骤 7：L2 文档列表服务端分页

1. 新建文档级索引表（SQLite 或 Chroma 旁表）：doc_id、chunks、total_chars、ingested_at；入库/删除时增量维护。
2. kb 列表 API：page / page_size / sort；ingest 老库提供一次性 backfill 脚本。
3. frontend KnowledgeBaseView：改调分页 API，去掉客户端全量 sorted。
4. 测试：万级 doc_id 列表内存与时间。

### 步骤 8：Chroma 客户端单例

1. src/rag/chroma_client.py（或 retriever 模块）：进程级 get_chroma_client()；ingest、retriever、kb 列表、删除统一引用。
2. 应用 shutdown 钩子 close。
3. 测试：现有 rag ingest/retriever 用例仍绿。

### 步骤 9：统计与导出流式化

1. trace_store 概览：计数/均值 SQL 聚合；p50/p95 用分桶或采样，去掉 fetchall。
2. usage CSV：StreamingResponse 分批写行，不在 StringIO 堆 10 万行。
3. 测试：大时间范围 trace、大 CSV 导出内存。

### 步骤 10：长期堆积治理

1. 语义缓存 semantic_cache.py：启动或定时任务清过期；每用户/全局条数上限；单答案长度上限。
2. 本地模型 retriever/reranker：切换配置时 pop 旧缓存；@lru_cache(maxsize=1) 或显式 del。
3. Skill：会话只存 skill_id + hash；agent 每轮从磁盘组注入块，设 SKILL_INJECT_MAX_CHARS。
4. frontend：Composer 卸载/切会话 revoke 全部 previewUrl；versions 保留最近 5 个，旧版去掉 timeline。
5. frontend useChat：流式写 ref，requestAnimationFrame 或 50 ms 合并 setMessages；结束后再 Markdown。
6. learning_plan_store：delete_session 时调用 clear_loaded(session_id)。
7. 测试：24h 跑批或单测覆盖各上限。

### 步骤 11：条件项（按需）

1. 若线上 thinking_budget 高：tool_call_engine 只保留最近一轮 reasoning_content，或设 REASONING_MAX_CHARS。
2. 生产保持 IMP_METHOD=PYTHON；LANGCHAIN/AUTOGPT 并发隔离另开任务，不纳入本迭代。

### 每步通用验收

- 单元/接口测试通过。
- 1.6G VPS：执行前、峰值、结束后 60s 各记 avail_mb（见 memory 文档第 11 节场景表）。
- 配置项同步 .env.example、config.py、config_meta（有 UI 的项进设置页）。

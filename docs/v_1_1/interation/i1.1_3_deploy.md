> AgentA 上线部署

# 1. 方案对比

本地模型(embedding + rerank) + sentence-transformers + 带 GPU 的 VPS
VS
online API(embedding + rerank) + 轻量 VPS


| 维度     | 方案 A：本地模型 + GPU VPS                        | 方案 B：online API + 轻量 VPS                           |
| ------ | ------------------------------------------ | -------------------------------------------------- |
| 技术栈    | sentence-transformers 本地跑 embedding/rerank | 调云端 embedding/rerank API，主机只跑 web 服务               |
| 延迟     | 无网络往返，GPU 上 embedding/rerank 都快            | 有网络往返，国内厂商延迟低、海外较高                                 |
| 质量     | 取决于选的开源模型（bge-m3 / bge-reranker 已很好），自己调   | 一线模型稳定（bge-m3、Cohere/Jina rerank、text-embedding-3） |
| 成本     | GPU VPS 固定月费，几百~上千/月，是主要开销                 | 按量计费，小流量几乎免费；轻量 VPS 几十/月                           |
| 成本随量变化 | 固定，量再大也不涨（量大反而摊薄划算）                        | 线性增长，量特别大时会超过自建                                    |
| 安全/隐私  | 数据不出机，最好，适合敏感/合规场景                         | 数据要发第三方，有隐私和合规风险                                   |
| 运维     | 自己管 GPU 驱动、模型下载、显存、版本；冷启动加载模型慢             | 省心，不管算力，厂商侧弹性扩容                                    |
| 可扩展    | 受单机/单卡限制，并发有上限                             | 天然弹性，扩容在厂商侧                                        |
| 国内访问   | 无外部依赖，不受网络管制影响                             | 海外 API 有访问/延迟问题，需选国内厂商规避                           |
| 可用性    | 只依赖自己这台机                                   | 受第三方 API 可用性影响                                     |


- 数据敏感 / 要离线 / 长期高流量 → 方案 A（GPU 月费值回票价）
- 量小 / 想省钱省心 / 数据不敏感 → 方案 B => 选中



# 2. 实现方案B



## 2.1. 实现 online API



### 2.1.1. API 选择

结论：选硅基流动 SiliconFlow（embedding + rerank 都用它）。

候选对比（均需同时提供 embedding + rerank 两种 API）：


| 维度          | 硅基流动 SiliconFlow                                                                       | 阿里百炼 DashScope                                                         |
| ----------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 模型          | 直接托管 `BAAI/bge-m3`（embedding）+ `BAAI/bge-reranker-v2-m3`（rerank）——就是 AgentA 现在本地这批开源模型 | 自家 `text-embedding-v4` + `qwen3-rerank`（`gte-rerank` 已于 2026-05-30 下线） |
| 迁移成本        | 极低：同款 bge 模型，向量空间一致，阈值几乎不用重调                                                           | 高：换自家模型 → 全量重灌向量库 + 重新校准阈值，rerank 分布也变                                 |
| 与阿里云 VPS 同云 | 独立厂商，从 VPS 走公网                                                                         | 阿里云自家，同地域内网延迟极低、流量可能省                                                  |
| key 复用      | 全新厂商，需新注册 + `api_keys.py` 加一项                                                          | `qwen` provider 已用 DashScope（`QWEN_API_KEY`），账号体系可复用                   |
| 计费          | bge-m3 / reranker Pro 版 ¥0.07/1M token；新用户 14 元额度                                      | text-embedding-v4 ¥0.5/1M；开通 90 天内 100 万 token 免费                      |
| 模型下线风险      | 跑开源 bge，相对稳定                                                                           | gte-rerank 刚下线换代，自家模型有被动失效风险                                           |


选硅基流动的三条理由：

1. 同款模型，迁移最平滑。硅基跑的就是本地这批 bge 模型，方案 B 最大的风险——"换 embedding = 向量库全废 + 阈值重调 + rerank 分布漂移"——几乎被消除。同一份 bge-m3 权重，本地与 API 产出的向量基本对齐。
2. 同云延迟优势对本场景收益有限。embedding/rerank 调用量小（几条 query + 几十个候选对），公网比内网多的 100~200ms，相比 LLM 生成的数秒可忽略，不足以抵消换模型的重灌 + 校准代价。
3. 向量库大概率免重灌（见下）。

关键红利：kb_m3 已用本地 bge-m3 灌好 2852 条（`rag_cli status` 实测，当前激活模型就是 m3）。选硅基同款 bge-m3，理论上库不用重灌，只需把 query 编码从本地换成 API；rerank 无持久化状态，换 API 永远不涉及重灌。

### 2.1.2. 注册 + 快速验证

1. 注册硅基流动、拿 API key，确认 embedding（`POST /v1/embeddings`，`BAAI/bge-m3`）和 rerank（`POST /v1/rerank`，`BAAI/bge-reranker-v2-m3`）两个端点能通。
  - 官网首页：[https://siliconflow.cn](https://siliconflow.cn)
  - 控制台 / 注册登录：[https://cloud.siliconflow.cn](https://cloud.siliconflow.cn)
  - API 密钥管理页（登录后新建 key，形如 `sk-...`）：[https://cloud.siliconflow.cn/account/ak](https://cloud.siliconflow.cn/account/ak)
  - 模型广场（找 `BAAI/bge-m3`、`BAAI/bge-reranker-v2-m3`）：[https://cloud.siliconflow.cn/models](https://cloud.siliconflow.cn/models)
  - Base URL：`https://api.siliconflow.cn/v1`；实名认证后可用免费模型额度（新用户另送 14 元额度）。
2. 快速验证（免重灌的 go/no-go 门）：拿几条相同文本，本地 bge-m3 与硅基 API 各编码一次，比 cosine。
  - 只需 key + 一个抛弃型小脚本，不依赖代码改造。
  - cosine ≥ 0.999 → 向量空间对齐，kb_m3 免重灌成立，可进 3.1.3。
  - 若漂移明显 → 说明后续要用 API 重灌 kb_m3，提前暴露，避免带着错误假设改代码。

验证结论（已完成，2026-07-07）：

- 端点连通，已验证：embedding（返回 1024 维）、rerank（相关句 0.99、无关句 0.00）均正常。
- 向量空间对齐，已验证 → kb_m3 免重灌。两种方法互证：
  - 本地 vs API 直比：同文本逐条 cosine，最低 0.9994、平均 0.9999。
  - 自检索：kb_m3 已存 chunk 用 API 重编码回查，命中自己 cosine 最低 0.9998。
- 实现时只需把 query 编码从本地换成 API，现有 2852 条向量不动。

#### 2.2.2.0. 配 GitHub Deploy Key

repo 是私有的，用只读 Deploy Key 让 VPS 能 clone。

```bash
ssh-keygen -t ed25519 -C "agenta-vps-deploy" -f ~/.ssh/agenta_deploy -N ""
cat ~/.ssh/agenta_deploy.pub   # 复制公钥
```

`ssh-keygen` 生成一对密钥：私钥 `agenta_deploy`（不外传）+ 公钥 `agenta_deploy.pub`（贴到 GitHub）。

把公钥加到 GitHub（网页操作）：

1. 浏览器打开 AgentA 仓库 → 顶部 Settings（仓库级，不是账号级）
2. 左侧菜单 Security → Deploy keys → 右上 Add deploy key
3. Title：填个能认出机器的名字，如 `aliyun-vps-hangzhou`
4. Key：粘贴 `cat ~/.ssh/agenta_deploy.pub` 的整行内容（`ssh-ed25519 AAAA... agenta-vps-deploy`）
5. Allow write access：不勾（只读拉代码足够，更安全）
6. 点 Add key 完成

再让 VPS 的 SSH 对 github 用这把 key。

为什么要这步：我们生成的私钥是自定义名字 `agenta_deploy`，SSH 默认只会自动找 `id_ed25519` / `id_rsa` 这类默认名，不会自动用它。写一段 `~/.ssh/config` 告诉 SSH：「连 github.com 时，就用 `agenta_deploy` 这把私钥」。

下面这条命令把配置追加（`>>`）到 `~/.ssh/config`（没有会自动建），`<<'EOF' ... EOF` 之间是要写入的内容：

```bash
cat >> ~/.ssh/config <<'EOF'
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/agenta_deploy
  IdentitiesOnly yes
EOF
chmod 600 ~/.ssh/config
```

配置项逐行含义：


| 行                                   | 含义                                      |
| ----------------------------------- | --------------------------------------- |
| `Host github.com`                   | 下面几行只对连接 `github.com` 生效                |
| `HostName github.com`               | 实际要连的主机名                                |
| `User git`                          | 用 `git` 这个用户登录（GitHub 的 SSH 固定用 git 账号） |
| `IdentityFile ~/.ssh/agenta_deploy` | 指定用这把私钥（就是刚生成的 Deploy Key 私钥）           |
| `IdentitiesOnly yes`                | 只用这把 key，别把机器上其它 key 也一股脑试一遍            |


`chmod 600` 把 config 权限收紧到「只有本人可读写」，否则 SSH 会因权限过松而拒绝读取。

最后验证连通：

```bash
ssh -T git@github.com
```

- 第一次连会问 `Are you sure you want to continue connecting (yes/no)?` → 输 `yes` 回车（把 github 加进 known_hosts）。
- 成功会显示：`Hi michaelwangzhenan/AgentA! You've successfully authenticated, but GitHub does not provide shell access.`（后半句说「不提供 shell」是正常的，不是报错）。

9.3 配 nginx：托管 dist 静态文件 + 反代 `/api` → 后端。SSE 流式回答（chat 思考过程）需要关掉 nginx 缓冲，否则会卡住不流式：

```bash
sudo tee /etc/nginx/sites-available/agenta > /dev/null <<'EOF'
server {
    listen 80;
    server_name _;

    root /root/AgentA/frontend/dist;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection '';
        proxy_buffering off;       # SSE：禁 nginx 缓冲，否则等整段响应结束才一次性下发
        proxy_cache off;
        proxy_read_timeout 3600s;  # 长会话防超时断连
        gzip off;                  # 全局 gzip 开着时也会缓冲 SSE
        client_max_body_size 10m;  # 上传文件大小限制
    }

    location / {
        try_files $uri /index.html;   # SPA 路由回退
    }
```

## 3.8. 配置 swap

正式 VPS 为 2GiB 内存，后端（chroma + torch）+ MCP 子进程常驻约 800MB+，available 余量不大。Ubuntu 默认无 swap，内存一紧内核可能 OOM kill 掉 agenta-backend（占内存最大的进程）。磁盘 40GiB 充裕，划出 2GiB 做 swap 成本低，建议新机上线后配好。

原理：swap（交换空间）是磁盘上的一块区域。物理内存不够时，内核把暂时不用的内存页写到 swap，腾出 RAM 给更急需的进程；之后进程再访问这些页时，从 swap 读回（对程序透明，但磁盘比 RAM 慢得多）。

| 场景 | 行为 |
| --- | --- |
| 内存充裕 | swap 基本不用，`Swap used` 多为 0 或很小 |
| 短时尖峰（大请求、备份打包、装依赖） | 换出冷页，避免立刻杀进程 |
| 长期内存不够 | swap 持续占用且系统变慢——该减负载或升配，不能靠 swap 硬扛 |

内核有个参数 swappiness（0–100），控制内存还够时是否主动把冷页换出去。默认 60 偏积极；小内存 VPS 建议设为 10，减少无谓换页。

配置步骤：

在 VPS 上执行（只需做一次；`fallocate` 失败时改用 `sudo dd if=/dev/zero of=/swapfile bs=1M count=2048 status=progress`）：

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-swappiness.conf
sudo sysctl -p /etc/sysctl.d/99-swappiness.conf
```

验证：

```bash
free -h                  # Swap 行应显示 total 2.0Gi
swapon --show            # 确认 /swapfile 已启用
cat /proc/sys/vm/swappiness   # 预期 10
```

注意：

- swap 是保险，不是扩容 RAM；日常性能仍取决于物理内存是否够用。
- 若 agenta-backend RSS 持续爬升、或 available 长期 < 200Mi，除观察是否内存泄漏外，应考虑关掉不用的 MCP 或升配到 4GiB。
- 查看内存占用：`free -h`；按进程：`ps aux --sort=-%mem | head -20`。

### 低内存并发与 SSE

1.6GiB~2GiB VPS 建议在 .env 收紧并发，避免多路 Agent / 深度研究子代理叠加打满内存：

```bash
MAX_CONCURRENT_AGENT_RUNS=1
DEEP_RESEARCH_MAX_PARALLEL_SUBAGENTS=1
INGEST_MAX_CONCURRENT=1
SSE_QUEUE_MAXSIZE=128
BM25_INDEX_CACHE_MAX=1
BM25_INDEX_IDLE_RELEASE_SEC=60
```

说明：

- MAX_CONCURRENT_AGENT_RUNS 控制同时在跑的 agent.run 数，超出排队。
- SSE_QUEUE_MAXSIZE 限制流式事件队列；慢客户端时满队列会丢弃可合并的 token/thinking 进度帧，final_answer / error 仍保证下发。
- BM25_INDEX_CACHE_MAX=1 限制进程内只常驻一个 collection 的 BM25 索引；检索结束后 BM25_INDEX_IDLE_RELEASE_SEC 秒内无新检索则释放。
- 前端 AbortController 断开 SSE 后，后端设协作式取消标志，Agent / 深度研究在轮次边界尽早退出。

## 3.9. 停止服务

维护、大版本迁移、或实例即将回收时，需要主动停掉 AgentA。线上两个进程：`agenta-backend`（后端）+ `nginx`（静态页 + `/api` 反代）。

| 目标 | 停什么 | 外部表现 |
| --- | --- | --- |
| 只动后端（改依赖、还原数据） | `agenta-backend` | 页面能开，问答 / API 502 |
| 只挡对外访问（后端还在本机跑） | `nginx` | 浏览器打不开；`curl 127.0.0.1:8000/api/health` 仍通 |
| 整站下线 | 两个都停 | 页面与 API 均不可用 |

临时停止（维护完还要再起来；enable 状态不动，重启 VPS 后会自动拉起）：

```bash
# 按需选一种或组合
sudo systemctl stop agenta-backend
sudo systemctl stop nginx

# 整站一次停
sudo systemctl stop agenta-backend nginx
```

确认已停：

```bash
sudo systemctl is-active agenta-backend nginx   # 预期均为 inactive
curl -s http://127.0.0.1:8000/api/health; echo  # 后端停时应连不上
curl -I http://127.0.0.1/                       # nginx 停时应连不上
```

恢复（与 3.4 更新后重启相同）：

```bash
sudo systemctl start agenta-backend
sudo systemctl start nginx
sudo systemctl status agenta-backend nginx --no-pager
curl -s http://127.0.0.1:8000/api/health; echo
curl -I http://127.0.0.1/
```

长期下线（实例要释放、不希望开机自启）：先停再 disable：

```bash
sudo systemctl stop agenta-backend nginx
sudo systemctl disable agenta-backend nginx
```

重新上线时记得 `enable` 回来：

```bash
sudo systemctl enable agenta-backend nginx
sudo systemctl start agenta-backend nginx
```

注意：

- `stop` 只停当前进程；未 `disable` 时，VPS 重启后 systemd 仍会把服务拉起来。
- 停后端会一并结束 MCP 子进程；正在进行的聊天请求会中断。
- crontab 定时备份（3.5 / 10.4.3）不依赖后端进程，凌晨 3 点仍会执行；若要一并暂停，用 `crontab -e` 注释掉对应行。
- 试用机路径为 `/root/AgentA`，正式机为 `/home/admin/AgentA`（见 4.1.2）；停启命令与路径无关，都是 systemd 服务名。

## 4.5. HTTPS 配置

前提：域名已备案 + DNS A 记录已解析到 VPS IP，解析生效后再做此步。


### 4.5.1. 装 Certbot

```bash
sudo apt install -y certbot python3-certbot-nginx
```

### 4.5.2. 签发证书

```bash
sudo certbot --nginx -d agenta.xin -d www.agenta.xin
# 按提示：输入邮箱（接收到期提醒）→ 同意条款 → 选 2（重定向，80 自动跳 443）
```

Certbot 会自动：
- 签发 Let's Encrypt 证书（90 天有效）
- 修改 nginx 配置（加 443 监听 + 80 → 443 的 301 重定向）
- 注册 systemd timer 自动续签（无需手动干预）

#### 已知坑：证书装不进 nginx

2.2.2.10 步骤 9.3 初版 nginx 使用 server_name _（通配，方便先用 IP 调试）。Certbot 按域名匹配 server 块；对不上时证书能签下来，但装不进 nginx：

```
Successfully received certificate.
...
Could not install certificate
Could not automatically find a matching server block for agenta.xin.
Set the `server_name` directive to use the Nginx installer.
```

此时证书已在 /etc/letsencrypt/live/agenta.xin/，nginx 尚未配上 HTTPS。

这与项目部署在 admin 目录、用 root 执行 certbot 无关——certbot 本就需要 root。只需改 nginx 的 server_name，并确认 root 仍指向实际静态目录（正式机一般为 /home/admin/AgentA/frontend/dist）。

修复：

```bash
# 1. 确认 root 路径（别改错）
sudo cat /etc/nginx/sites-available/agenta

# 2. 把 server_name _ 改成域名
sudo sed -i 's/server_name _;/server_name agenta.xin www.agenta.xin;/' /etc/nginx/sites-available/agenta

# 3. 检查并重载
sudo nginx -t
sudo systemctl reload nginx

# 4. 把已有证书装进 nginx（不必重新签发）
sudo certbot install --cert-name agenta.xin
# 提示是否重定向 HTTP → HTTPS 时选 2
```

验证：

```bash
curl -I https://agenta.xin/   # 200
curl -I http://agenta.xin/    # 301 → https
```

若 install 仍失败，需手动补 443 的 server 块，ssl_certificate 指向 fullchain.pem 与 privkey.pem（路径见 Certbot 报错）。/api/ 反代须保留 proxy_buffering off 等项，见 4.5.4。

HTTPS 生效后 nginx 只响应域名，裸 IP 会 404；可选补救见 4.5.6。

### 4.5.3. 验证自动续签

```bash
sudo systemctl status certbot.timer   # 应显示 active (waiting)
sudo certbot renew --dry-run          # 模拟续签，确认无报错
```

### 4.5.4. 检查 nginx 配置

Certbot 自动改了 nginx，但需确认 SSE 反代配置还在（proxy_buffering off 等）：

```bash
sudo cat /etc/nginx/sites-available/agenta   # 确认 /api/ 块里 proxy_buffering off 还存在
sudo nginx -t
sudo systemctl reload nginx
```

若 Certbot 覆盖了 `/api/` 块的配置，手动把 2.2.2.10 步骤 9.3 的配置补回去。

### 4.5.5. 验证

```bash
curl -I https://agenta.xin/    # 应返回 HTTP/2 200
curl -I http://agenta.xin/     # 应返回 301 → https
```

浏览器打开 `https://agenta.xin`，看到绿色锁标 + 正常页面，聊天流式输出正常，即完成。

### 4.5.6. 裸 IP 访问

4.5.2 将 server_name 改为域名并完成 HTTPS 后，用 VPS IP 访问 http://47.96.93.237 不再匹配任何 server 块，nginx 返回 404。https://agenta.xin 不受影响。

适用场景：本地调试，或个别网络下域名暂时不可用。注意：不能指望借此绕过公司上网代理——例如 Zscaler 按「新注册域名」拦截时，直连 IP 也常被封。

在 /etc/nginx/sites-available/agenta 文件末尾追加一个仅监听 80、server_name 为 VPS IP 的 server 块。证书只签给域名，IP 入口仅提供 HTTP，不做跳转到 HTTPS。

正式机静态目录为 /home/admin/AgentA/frontend/dist；试用机改为 /root/AgentA/frontend/dist。以下以正式机 IP 47.96.93.237 为例：

```bash
sudo tee -a /etc/nginx/sites-available/agenta > /dev/null <<'EOF'

server {
    listen 80;
    server_name 47.96.93.237;

    root /home/admin/AgentA/frontend/dist;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection '';
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
        gzip off;
        client_max_body_size 10m;
    }

    location / {
        try_files $uri /index.html;
    }
}
EOF

sudo nginx -t
sudo systemctl reload nginx
```

验证：

```bash
curl -I http://47.96.93.237/   # 应 200
```

注意：裸 IP 加 HTTP 属于非安全上下文，浏览器中 crypto.randomUUID 等接口可能不可用，见 i1.1_6_randomUUID.md。日常使用 https://agenta.xin 即可。
